# Phase 0 — Project Analysis and Safety Baseline

**Project:** Calibration & Validation Management System  
**Target:** Polarimeter validation  
**Analysis date:** 2026-11-16  
**Baseline:** `main` at `6957f94dc2e651a40dff5fcc2fdc8977e5b88a30`; work is isolated on `feat/polarimeter-validation-upgrade`.

## Source and preservation baseline

The MediaFire archive was downloaded and verified as a valid ZIP. Its embedded source revision is `6957f94dc2e651a40dff5fcc2fdc8977e5b88a30`; the current GitHub `main` checkout is the same revision. The seven requested source files checked against the archive are byte-for-byte identical. The Git baseline is clean, so the branch and original `main` remain recoverable.

The current repository—not the archive—is treated as authoritative if the two diverge during implementation. No project code was executed before inspection. No unrelated instrument modules or historical records are intended to be replaced.

## Actual architecture inspected

- React 19, TypeScript, Vite, Tailwind, Recharts, jsPDF, and a shared set of UI components.
- Express/tRPC with React Query; authenticated procedures are separated into `protectedProcedure`, `editorProcedure`, and `adminProcedure`.
- Device metadata and initial limits are defined in `client/src/lib/qc.ts`. Existing instrument-profile overrides are loaded from the existing equipment register and applied to the same device registry.
- Validation forms are implemented in `client/src/components/CalibrationForm.tsx`; `client/src/pages/Home.tsx` hosts the form, result view, settings, and navigation.
- Validation records store generic `resultData` JSON. SQLite stores it as text in `validation_records.result_data`; Supabase stores it as JSONB. Settings are stored in the existing `validation_settings` table in both providers.
- Local SQLite tables are initialized idempotently in `server/localDb.ts`; Supabase schema is maintained in `server/sql/supabase_schema.sql` and accessed through `server/supabaseDb.ts`.
- The existing record lifecycle is `draft`, `approved`, or `rejected`. Admin approval/rejection is performed by `records.decide`; audit events and approval rows are already recorded. The form itself currently exposes a separate local approval dropdown, which is not authoritative.
- Official reports are generated by `client/src/lib/officialPdf.ts`; the Polarimeter has a dedicated `polarimeterLayout()`.
- Tests use Vitest. Existing server recalculation coverage is limited to Disintegration; there is no Polarimeter server-calculation suite.

## Existing Polarimeter behavior and gaps

1. `qc.ts` defines the existing profile `QC-I-029`, Bellingham & Stanley ADP220, serial `PE99003`, SOP `QC-032D`, form `QC-032B-01`, and the current settings (2 dm; specific rotation 66.3–67.0; repeatability 0.05; correlation 0.99).
2. `CalibrationForm.tsx` initializes Polarimeter optical rotation, concentration, six repeat readings, and four linearity readings with demonstration values. The form calculates on the client and returns generic rows, metrics, and chart points; it does not preserve a complete, typed set of original Polarimeter inputs.
3. `server/validationRecompute.ts` assumes exactly eight Polarimeter result rows: one calculated accuracy result, six readings compared to the first reading, and one linearity result. It uses fixed concentrations `[10, 20, 30, 40]` and validates only submitted row statuses; it does not recalculate specific rotation from α, tube length, and concentration or recompute slope/intercept/R².
4. `Home.tsx` saves completed results as drafts, but a local dropdown can make an unsaved PDF appear approved/rejected. RecordHistory is the existing server-authoritative admin decision path.
5. `approveValidationRecord` currently permits a failed result to be marked approved; server-side protection is required. The record API already checks roles, but a secure signature is not implemented and must not be claimed.
6. `polarimeterLayout()` contains fallback/example readings and metrics (including rotation, concentration, readings, concentrations, slope, intercept, and correlation). It also connects data points rather than plotting a calculated least-squares regression line.
7. Draft inputs are not recovered after navigation/reload, and there is no record version/concurrency token. Existing generic settings contain no version history.
8. Project reference notes confirm a Polarimeter paper-form layout and X/Y relationship, but the approved SOP QC-032D itself is not present in the inspected source. Consequently the initial limits, repeatability basis, count, nominal points, temperature, and wavelength cannot be certified from the repository. These parameters must be visibly marked **Pending Verification**; no new scientific limit will be invented.

## Required changes and implementation plan

### Front end

- Keep the existing application and instrument registry. Replace only the Polarimeter form branch with an integrated, English/LTR, responsive step-based workflow.
- Start actual measurement fields blank. Retain only documented protocol conditions/reference points as prefilled read-only values.
- Preserve original inputs in a versioned Polarimeter payload; calculate specific rotation, repeatability statistics, and least-squares linearity from those inputs.
- Provide progress navigation, per-step validation, local draft recovery, clear calculated/reference/input distinctions, and a protocol verification warning.
- Retain other instrument forms unchanged.

### Protocol and data model

- Use a typed, versioned protocol snapshot inside each new Polarimeter record so a record retains the settings/formulas/nominal points used at execution even if settings change later. Do not rewrite historical result JSON.
- Keep the current acceptance values as unverified initial settings only. Block successful formal approval while the Polarimeter protocol is pending SOP verification.
- Prefer additive changes to the existing JSON record/settings schema over replacing tables. If a database change is required, implement it for SQLite and Supabase and document migration/rollback.

### API and server verification

- Add a versioned schema for Polarimeter original inputs and validate its shape at the tRPC boundary.
- Independently recalculate accuracy, configured repeatability evaluation/statistics, regression slope/intercept/r/R², and statuses on the server; reject incomplete or inconsistent submissions.
- Preserve existing validation behavior for the other seven instrument keys.
- Block approval of failed records and prevent protocol-pending Polarimeter records from being approved as successful.

### PDF, audit, and workflow

- Remove fabricated Polarimeter fallback values; render missing data as missing, not as reference readings.
- Use actual point coordinates and the computed regression line; distinguish `r` from `R²`.
- Make new-form PDFs explicitly draft/unapproved and use the saved record lifecycle for saved-record PDFs.
- Continue using existing audit and approval paths; do not claim secure electronic signatures or a separate reviewer/approval capability that the current architecture does not provide.

### Tests and safety

- Add calculation, edge-case, tampering, failure-blocking, and PDF regression tests while retaining all existing tests.
- Run type checking, full Vitest suite, and production build. Review the final diff to ensure unrelated instrument behavior and historical data remain untouched.

## Dependencies and risks

No additional runtime dependency is expected: `jspdf`, `recharts`, React, tRPC, Zod, SQLite, and Supabase support already exist. Supabase end-to-end tests require the project's external environment and credentials, which are not included in the source archive; local SQLite and static schema checks can still be run here. Visual/browser verification may also be limited by the absence of a supplied QC-032D SOP and a real authenticated lab environment.

## Phase 0 conclusion

The source baseline is preserved and inspected. Work can proceed as a focused additive enhancement, with SOP-dependent protocol approval explicitly gated rather than guessed. The known architectural limitations—no secure electronic-signature implementation, no distinct technical-review lifecycle, and no server-backed incomplete-draft/concurrency workflow—will be reported honestly if they remain outside a safe incremental change.
