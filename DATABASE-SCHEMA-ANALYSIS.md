# Database Schema Analysis: `retest_of_record_id`

**Date:** 2026-11-19
**Symptom (production, Vercel + Supabase):**
`Supabase request failed (400): Could not find the 'retest_of_record_id' column of 'validation_records' in the schema cache`

## 1. Why the application sends `retest_of_record_id`

| Layer | Location | Behaviour |
|---|---|---|
| Client | `client/src/pages/Home.tsx` → `trpc.records.save` | Sends `retestOfRecordId` / `retestReason` only when a retest context exists |
| Supabase adapter | `server/supabaseDb.ts` `createValidationRecord()` | **Always** includes `retest_of_record_id: input.retestOfRecordId ?? null` and `retest_reason` in the `POST /rest/v1/validation_records` body. This is correct: ordinary records store `NULL` |
| Supabase adapter | `updateValidationRecord()` | `PATCH` is filtered by `record_version=eq.N`, so it also needs the migrated `record_version` column |
| Row mapping | `mapRecord()` | Reads `retest_of_record_id`, `retest_reason`, `record_version` |
| SQLite adapter | `server/localDb.ts` | Same fields, stored as `INTEGER` |

The field is part of the architecture: controlled Polarimeter retests link to the failed original, and the failed record stays immutable. Removing it, or dropping it from payloads, is not acceptable (see project rules).

## 2. What the deployed database contains

| Source | `validation_records` definition |
|---|---|
| `server/sql/supabase_schema.sql` (base schema, applied at first setup) | `id bigint generated by default as identity primary key`, **no** `record_version`, `retest_of_record_id`, `retest_reason` |
| `server/sql/polarimeter_workflow_migration.sql` (additive) | Adds `record_version integer NOT NULL DEFAULT 1`, `retest_of_record_id bigint REFERENCES validation_records(id) ON DELETE RESTRICT`, `retest_reason text`, the four Polarimeter tables, guard triggers and RPC functions |
| `FINAL-COMPLETION-REPORT.md` / delivery notes | State explicitly that the Supabase migration **was not applied to a live database** |

**Root cause:** the application code was deployed, but the additive migration was never applied to the production Supabase project. PostgREST validates every request body against its schema cache. The column does not exist there, so the request is rejected with `PGRST204` (HTTP 400) before any row is written.

This is not a schema-cache staleness problem caused by a missing reload: the column was never created. The original migration also had no `NOTIFY pgrst, 'reload schema'`, so even a manual `ALTER TABLE` could have left a stale cache for a short time. The updated migration fixes both.

**Expected collateral failures with the same cause:**
- `polarimeter_drafts` missing → server draft autosave fails (the UI showed only "Server draft: offline").
- `record_version` missing → draft updates fail.
- `record_approvals.reason`, review, deviation and RPC objects missing → technical review, CAPA and approval workflows fail.

## 3. Key and relationship types

| Item | Supabase | SQLite |
|---|---|---|
| `validation_records.id` | `bigint` identity | `INTEGER PRIMARY KEY AUTOINCREMENT` (64-bit) |
| `retest_of_record_id` | `bigint`, NULL, FK → `validation_records(id)` `ON DELETE RESTRICT` | `INTEGER`, NULL, `REFERENCES validation_records(id)` |
| Parent index | `validation_records_retest_parent_idx` (partial, `IS NOT NULL`) | Same name and definition (added in this fix) |
| Retest rules | Trigger `validate_polarimeter_retest_link` (failed Polarimeter original, same equipment, reason ≥ 10 chars) | Triggers in `localDb.ts` with the same rules |
| Failed-record immutability | Triggers `polarimeter_failure_record_immutable` / `_no_delete` | Equivalent triggers |

`bigint` matches the primary key, so no UUID or TEXT type is involved. The migration now aborts if `validation_records.id` is not `bigint`.

## 4. Verification of the actual deployed schema

This development sandbox cannot open network connections to `*.supabase.co`, and the leaked credentials in the repository history were deliberately **not** used. The deployed schema is verified through the application itself:

`GET https://calibration-silk.vercel.app/api/health/schema`

The deployed server uses its own Vercel environment variables to make read-only `select=<columns>&limit=0` probes. These go through the same PostgREST schema-cache validation that produced the 400 error. The response contains only booleans, missing column names, and a 6-character project-ref hint. The hint confirms the app is connected to the intended project.
